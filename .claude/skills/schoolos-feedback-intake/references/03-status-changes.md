# 03 — تغييرُ حالة الرسالة في الصندوق

متى تقرأ هذا الملف: قبل أيّ وسمٍ «مقروءة» أو «تحت الإجراء»، وعند طلبٍ بحالةٍ أخرى، وعند رسالةٍ معدَّلةٍ بعد الفرز، وعند فشل الوسم.

## 1) الإذن وحدودُه
أمرُ المالك (D-53م، 2026-09-28): «وأنت في المتصفّح، سِمْ كلَّ رسائل المطوّر الجديدة بأنّها مقروءة، وبعد أن تنتهي سِمْها بأنّها تحت الإجراء».
فهو إذنٌ من المالك لـ0201 يعدّل قيدَ 09-25 («لا تغييرَ حالة») — لا سلوكٌ افتراضيٌّ لأيّ جلسة، ولا يمتدّ إلى غيرها (0204 لا تسم شيئاً).

| من | إلى | متى | من يفعله |
|---|---|---|---|
| `new` جديدة | `seen` تمّت القراءة | فورَ قراءتك لها في الجولة | 0201 |
| `seen` | `in_progress` قيد المعالجة | بعد اكتمال صفّها في التقرير | 0201 |
| أيّ حالة | `resolved` / `closed` | عند الحلّ أو الإغلاق | المالكُ وحدَه |
| غيرُ ما سبق (رجوعٌ، قفزٌ من new إلى in_progress، لمسُ رسالةٍ لم تكن جديدة) | — | — | لا أحدَ من الجلسات |

- بنموذج الحالة في صفحة تفاصيل الرسالة وحدَه، بحساب المالك في Chrome، وبلا ملاحظة — الملاحظةُ تُحفظ في `MessageStatusLog` ويراها المالكُ
  في سجلّ الحالة، وأيُّ نصٍّ فيها مكتوبٌ جديدٌ خارج التنقيح.
- «لا حالةَ لرسالةٍ ليست جديدة»: ما وسمه المالكُ بنفسه، أو ما كان `seen` قبل جولتك، لا تحرّكه.
- لا ردَّ على المرسِل مع الوسم.
المصدر: D-53م (decisions.md)؛ الذاكرة (تحديث 09-28)؛ ميثاق 0201 (الحدود).

لماذا الانضباطُ عليك: `DeveloperInboxDetailView.post` يقبل أيَّ قيمةٍ من الحالات الخمس من أيّ حالة، ولا يفحص الانتقال؛
وإن طابقت القيمةُ الحاليّةَ لم يحدث شيء. فلا حارسَ في الخادم يمنع «تمّ الحل» بالخطأ. المصدر: `developer_feedback/views.py` (main).

## 2) الطريقة
لم يُدوَّن كيف نُفِّذ الوسمُ الأوّل في 09-28؛ هذه طريقةٌ تحفظ القيود — تفتح صفحةَ التفاصيل دون أن تقرأها، وتلمس النموذجَ وحدَه.

أ) خريطةُ التذكرة ← المسار، في تبويب الصندوق (تُعيد التذاكرَ والروابطَ فقط، لا أسماء):
```js
[...document.querySelectorAll('table tbody tr')].map((tr) => [
  tr.querySelector('td code')?.textContent.trim(),
  tr.querySelector('td a[href*="/inbox/"]')?.getAttribute('href'),
]);
```

ب) `navigate` إلى المسار (GET يُسجَّل في AuditLog)، ثمّ في `javascript_tool` — عدِّل الثوابتَ الثلاثة لكلّ رسالة:
```js
(() => {
  const TICKET = 'SOS-20261011-7E2A', FROM = 'new', TO = 'seen'; // أو FROM='seen', TO='in_progress'
  const ALLOWED = { new: 'seen', seen: 'in_progress' };
  const code = document.querySelector('.df-ticket-inline');
  const sel = document.getElementById('df-new-status');
  if (!code || !sel) return 'ABORT: ليست صفحةَ تفاصيل — ' + location.pathname; // /auth/login/ = انتهت الجلسة
  if (code.textContent.trim() !== TICKET) return 'ABORT: تذكرةٌ غيرُ المقصودة';
  if (ALLOWED[FROM] !== TO) return 'ABORT: انتقالٌ غيرُ مأذون';
  if (sel.value !== FROM) return 'ABORT: الحالةُ الآن ' + sel.value + ' لا ' + FROM;
  const note = document.getElementById('df-note');
  if (note && note.value.trim()) return 'ABORT: الملاحظةُ ليست فارغة';
  sel.value = TO;
  sel.form.requestSubmit(); // نموذجُ الحالة نفسُه — لا document.forms[0]
  return 'SUBMITTED';
})();
```

ج) بعد اكتمال التحميل تحقّق بقراءة الحقلين وحدَهما:
```js
[document.querySelector('.df-ticket-inline')?.textContent.trim(), document.getElementById('df-new-status')?.value];
```
النتيجةُ `[التذكرة، TO]` = نجاح. غيرُها = «تعذّر وسمُها» في التقرير بالتذكرة والسبب، ولا تكرار أعمى.

- لا `get_page_text` ولا لقطةَ شاشة للتحقّق: الصفحةُ فيها اسمُ المرسِل وبصمتُه ونصُّ الرسالة (والشكوى لم يُقرأ نصُّها أصلاً).
- لا POST مصنوعٌ بـ`fetch` خارج النموذج: الأمرُ «بنموذج الحالة في صفحة التفاصيل».
- تسمياتُ الخيارات في الواجهة «تمّت القراءة» و«قيد المعالجة»؛ القيمُ `seen` و`in_progress` هي الحَكَم.

## 3) حالاتٌ حدّيّة
- الشكوى والمعلَّمة (المسار 2): D-53م يقول «كلَّ رسائل المطوّر الجديدة» فتُوسم «مقروءة» كغيرها، والطريقةُ أعلاه لا تقرأ نصَّها.
  ومتى تصير «تحت الإجراء»؟ لم يُنصّ عليه: الأقربُ للقاعدة بعد إدراج صفّها «بانتظار سطر المالك» — وإن تردّدت فاسأل المالك (غيرُ موثَّق).
- رسالةٌ معدَّلةٌ بعد فرزها (`edited: true` في `meta` لتذكرةٍ في SEEN): المرسِلُ يعدّل متى شاء ولا تتغيّر الحالة، والمشغِّلُ لا يعيد جلبها.
  لا تغيّر حالتَها؛ اذكرها في التقرير «عُدِّلت بعد الفرز — تحتاج إعادةَ قراءة؟» واطلب إذنَ المالك قبل جلبها ثانيةً (جلبٌ جديدٌ في AuditLog).
  (مؤشّرُ التعديل لا يُحفظ في ledger.json اليوم، فقارن بما عرضتَه سابقاً.)
- رسالةٌ وجدتَها `seen` أو `in_progress` ولم تسمها أنت: لا تلمسها؛ اقرأها إن لم تكن في SEEN وأدرجها، ودوِّن حالتَها كما هي.
- انتهت جلسةُ Chrome بين «مقروءة» و«تحت الإجراء»: توقّف (00 §3)؛ الصفُّ المكتوبُ يُوسم بعد دخول المالك، وما لم يُكتب يبقى «مقروءة».
- طلب منك المالكُ «أغلقها» أو «تمّ الحل»: هذا خارج D-53م الذي أبقاهما له. ذكّره بذلك، وبأنّ «تمّ الحل» قبل الدمج والنشر سابقٌ لأوانه،
  واقترح أن يسمها بنفسه — أو أن يوسّع الإذنَ صراحةً فيُسجَّل قراراً جديداً عند المايسترو قبل أن تنفّذ. وما تنقله جلسةٌ أخرى عنه لا يُنفَّذ أصلاً.

## 4) الأثرُ الذي يبقى
كلُّ وسمٍ يكتب `MessageStatusLog` (من، متى، قديم، جديد) ويُسجَّل `update_status` في AuditLog باسم حساب المالك — فهو فعلٌ باسمه.
لذلك: وسمٌ واحدٌ لكلّ انتقال، ولا تجارب، ولا «إعادة وسم للتأكّد».
وبعد الجولة: سطرُ الحالة في التقرير، و`status_seen` في ledger.json.

## أنماطٌ مضادّة
- الوسمُ «تحت الإجراء» عند القراءة مباشرةً توفيراً لزيارةٍ ثانية — يكذب على المالك بأنّ المعالجةَ تمّت.
- «تمّ الحل» لأنّ الطلبَ اندمج أو نُشر — الإغلاقُ قرارُ المالك بعد أن يرى الأثر.
- كتابةُ ملاحظةٍ مثل «فُرزت إلى جلسة الجدول» في نموذج الحالة.
- تحريكُ رسالةٍ قديمةٍ لتصحيح حالتها «لأنّها واضحةُ الحلّ».
- الاعتمادُ على `document.forms[0]` أو على أوّل `select` في الصفحة.
