# الدمجُ المتعثّر، والرجوع، والحوادثُ بعد النشر

متى تقرأ هذا الملف: طلبٌ خرج من الطابور بلا دمج، أو حالتُه UNMERGEABLE/DIRTY، أو رُفض دفعٌ بـGH006، أو مجموعةُ `merge_group` حمراء وفحوصُ الطلب خضراء؛ أو عطلٌ ظهر بعد نشرٍ وقرارُ رجوعٍ مطروح.

## 1) تشخيصُ الإقصاء
| ما تراه | معناه | المصدر |
|---|---|---|
| الإدخالُ اختفى و`merged` لم يرتفع بعد | سباقٌ معروف: يختفي الإدخالُ قبل الدمج بثوانٍ — اقرأ مرّتين بينهما 20 ث ولا تقدّمَ لـmain قبل إعلان الإقصاء | `reference_deploy_session_recipe_2026_09_26` |
| خرج بين 07:00 و14:00 في يوم دوام | حارسُ `deploy-window` لا عطل؛ يُعاد بعد 14:00 أو بـ«نشر-عاجل» بإذن | `project_deploy_window` |
| `UNMERGEABLE` | تعارضٌ مع main أو مع ما أمامه في الطابور، لا انتظارُ فحوص | `feedback_merge_queue_branch_lock` |

| `GH006 … merge queue` عند الدفع | الفرعُ مقفلٌ ما دام الطلبُ في الطابور | `feedback_merge_queue_branch_lock` |

## 2) الإخراجُ والإعادة
```bash
# معرّفُ العقدة (قراءة)
gh api graphql -F owner='{owner}' -F name='{repo}' -F n=<N> -f query='query($owner:String!,$name:String!,$n:Int!){repository(owner:$owner,name:$name){pullRequest(number:$n){id isInMergeQueue merged mergeStateStatus}}}'
# الإخراج (فعل) — طلبُك وحده، لا يمسّ غيرَه
gh api graphql -f query='mutation{dequeuePullRequest(input:{id:"<PR node id>"}){mergeQueueEntry{state}}}'
# بعد أن يدفع صاحبُه التصحيح (فعل)
gh pr merge <N> --auto
```
- الإخراجُ يُطفئ الدمجَ التلقائيّ، والإعادةُ قد لا تثبت من أوّل مرّة: تحقّق أنّ `isInMergeQueue: true` وإلّا أعِد. المصدر: `project_merge_queue`.
- `--disable-auto` لا يُخرج طلباً من الطابور. المصدر: مثله.
- المتراكب: أخرِجه، وادمج أساسَه، ثمّ يدمج صاحبُه `origin/main` في فرعه (بلا force) ويحسم بجانب فرعه ويتحقّق بـ`git diff origin/main...HEAD`، ثمّ يعود. المصدر: `reference_deploy_session_recipe_2026_09_26`.
- الحلُّ الترتيبيّ للتعارض الدلاليّ: الطلبُ الذي يملك الملفَّ المخالف يرحّله **قبل** حامل الحارس. المصدر: مثله.

## 3) حدُّ ما تُصلحه هنا وما يعود
| النوع | من يُصلح |
|---|---|
| بنيويٌّ صرف: ترتيبُ استيراد، `ruff --fix`، إعادةُ إدخالٍ أو تشغيل، تعارضٌ نصّيٌّ في جدولٍ مشترك يُحتفظ فيه بصفوف الطرفين | يجوز هنا |
| يمسّ منطقَ الميزة: RLS، حارسُ طبقاتٍ أو صلاحيّات، منطقُ عمل، اختبارٌ يفشل لسببٍ جوهريّ | **تشخّص وتخبر فقط** (الملفّ والسطر والسبب) ويعود لصاحبه في 04 |

- وقعت إصلاحاتٌ دفعتها جلسةُ النشر على فروع غيرها **بإذن مالكٍ صريحٍ في محادثتها** (#702) — الإذنُ الصريحُ لتلك المرّة شرط. المصدر: `reference_deploy_session_recipe_2026_09_26`.
- **مقترحٌ غيرُ مقرّر:** ميثاقُ 0601 يقترح أنّ «إعادةَ تأسيسٍ لا تغيّر السلوكَ تُنجز هنا، وما يغيّر السلوكَ يعود إلى 04 ثمّ 0501» — **بانتظار قرار المالك**؛ حتى يُقرّ: كلُّ تعديلٍ يغيّر ما عاينه المالكُ يعود للمعاينة، لأنّ سطرَ الاعتماد اعتمادٌ لما رآه. المصدر: `delivery_manager_work/docs/tab_charters.md` (ميثاقُ 0601).
- إصلاحٌ فشل مرّتين في CI: لا ثالثَ بالتخمين — تُعاد البوّابةُ محلّيّاً بالإصدارات المثبَّتة أوّلاً. المصدر: `feedback_reproduce_ci_before_refix`.
- رسالةُ الإعادة لصاحب الطلب: رقمُ الطلب، والفحصُ أو المجموعةُ الحمراء بمعرّف التشغيل، والسطرُ الدقيق، وما يلزم ليعود — وهل يلزمه عرضٌ جديدٌ على 8500.

## 4) عطلٌ بعد النشر
1. **صنّف** (مرجعُ المايسترو `delivery_manager_work/docs/incident_runbook.md`): S1 = الإنتاجُ متوقّفٌ أو خطأٌ يمسّ البياناتَ أو الأمنَ أو الخصوصيّة؛ أبلغ المالكَ والمايسترو فوراً بسطرٍ: ماذا، منذ متى، الأثر.
2. **جمّد** الطابور: لا إدخالَ جديداً حتى يُعلن الحلّ.
3. **حدّد آخرَ تغييرٍ منشور:** `commit` في `/health/` مقابل main، وما دُمج منذ آخر نشرٍ سليم (`git log <sha_سليم>..<sha_منشور> --oneline`).
4. **الاستعادةُ قبل التشخيص** — والرجوعُ بإذن المالك النصّيّ في محادثتك، وتنفيذُه بيده حيث يمسّ الإنتاج. المصدر: `incident_runbook.md` §2، `skills/maestro-incident`.
5. **الإغلاق:** سليمٌ ساعةً ← إعلانُ النهاية ← مراجعةٌ بلا لوم خلال 48 ساعة (خطٌّ زمنيّ من الأدوات، جذرٌ بنظامٍ لا بشخص، إجراءٌ بصاحبٍ وحارسٌ يقفل العودة وبندُ خارطة).
- حادثٌ يمسّ بياناتٍ شخصيّة: خطّةُ PDPPL في `docs/INCIDENT_RESPONSE.md` (التسجيلُ في تطبيق الخروقات والإبلاغُ خلال 72 ساعة) قرارُ المالك وتسجيلُه بيده.

## 5) طرقُ الرجوع
| الطريق | متى | ملاحظات |
|---|---|---|
| `rollback.yml` (افتراضيّ): طلبُ دمجٍ إيداعُه شجرةُ الهدف حرفيّاً | الحالُ العاديّ | يمرّ بالبوّابات والطابور كأيّ طلب — **ونافذةُ الدوام تسري عليه** فيلزمه «نشر-عاجل» بإذن؛ وبعد دمجه **لا ينشر Railway وحده** (النشرُ يدويٌّ منذ 09-18) بل يلزم أمرُ النشر بيد المالك. إن لم تبدأ فحوصُه: `gh pr close` ثمّ `gh pr reopen` |
| لوحةُ Railway: النشرُ السابقُ السليم ← Rollback (لكلّ خدمةٍ مسّها التغيير) | GitHub نفسُه معطّل، أو الأسرعُ في S1 | بيد المالك؛ ثمّ يُصلَح main بطلب رجوع، وإلّا أعاد النشرُ التالي الشيفرةَ المعطوبة |
| `gh workflow run rollback.yml -f commit_sha=<sha> -f verify_only=true` | بعد أيّ رجوع | يقارن `commit` في `/health/` بالهدف 18 محاولة |
- الهجراتُ لا تُرجع: راجع `git diff <sha>..main -- '*/migrations/*'` قبل الدمج؛ هجرةٌ حذفت عموداً ذهبت بياناتُه، وأُضيفت عموداً يبقى بلا شيفرة. المصدر: `rollback.yml`.
- `railway run python manage.py migrate …` الواردُ في `docs/deployment/runbook.md` §5 **لا يعمل**: يعمل على جهازك ولا يحلّ عنوانَ القاعدة الداخليّ؛ الأوامرُ داخل الحاوية بـ`railway ssh`. المصدر: `feedback_railway_run_vs_ssh`.
- معاييرُ القرار (`runbook.md` §4): `/health/` غيرُ 200 أو فسادُ بياناتٍ مشتبَه ← رجوعٌ فوراً؛ بطءٌ ← تحقيقٌ ثمّ رجوعٌ إن لم يُحلّ في 10 دقائق؛ بلاغُ مستخدمٍ واحد ← تحقيقٌ بلا رجوع.

## أنماطٌ مضادّة
- إعلانُ «أُقصي» من قراءةٍ واحدة، أو الاكتفاءُ بفحوص الطلب لتفسير أحمرِ المجموعة.
- كتابةُ إصلاحٍ منطقيٍّ في فرع جلسةٍ أخرى لأنّ الحلَّ «واضح».
- إصلاحٌ ثالثٌ بالتخمين في CI.
- `force-push` أو `--no-verify` لتسريع الإعادة (يحجبهما حارسُ غيت؛ انظر `schoolos-git-safety`).
- التشخيصُ الطويلُ والإنتاجُ معطّلٌ بينما رجوعٌ جاهز.
- افتراضُ أنّ دمجَ طلب الرجوع أعاد الإنتاج.
