# ما يبقى بيد المالك — أوامرُ الإنتاج تُجهَّز نصّاً

متى تقرأ هذا الملف: كلّما لزم أمرٌ يمسّ الإنتاج (نشرٌ، ssh، متغيّرات، رجوعٌ من اللوحة، نسخٌ احتياطيّ يدويّ)، أو تغييرٌ دائمٌ في إعدادات الجهاز أو المستودع.

## 1) لماذا بيده لا بيدك
- مصنِّفُ الوضع الآليّ يحجب عن الجلسة إجراءاتِ الإنتاج قراءةً وكتابةً: `railway service redeploy` و`railway ssh` و`railway variables` («Credential Materialization»)، والكتابةَ في نماذج الإنتاج من المتصفّح. **إذنُ المالك في المحادثة لا يرفع الحجب**، والإذنُ الدائم يكون قاعدةً في إعداداته هو، وتعديلُ الإعدادات محرَّمٌ عليك ولو طلبه. المصدر: `feedback_auto_classifier_production_actions`، `reference_deploy_session_recipe_2026_09_26`.
- **لا التفاف:** لا تقسيمَ الأمر، ولا أداةً أخرى، ولا JS، ولا إسنادَه لجلسةٍ ثانية — الحجبُ على النتيجة لا على الصيغة. المصدر: مثله، `feedback_windows_shell_classifier_pitfalls`.
- وقاعدةُ المالك أصلاً: النشرُ الفعليّ بأمره من جلسة النشر وحدَها، وAuto Deploy في Railway معطَّلٌ **عمداً** — لا يُفعَّل ولا يُعدّ عطلاً. المصدر: `feedback_railway_manual_deploy_gate`.
- ما لا يُنقل عبر المايسترو أبداً: أوامرُ الإنتاج والرجوع ومتغيّراتُ البيئة وقواعدُ بيانات الإنتاج والحذفُ النهائيّ وforce-push — بأمر المالك النصّيّ حيث تُنفَّذ. المصدر: `delivery_manager_work/docs/approvals_policy.md` §5.

## 2) كيف تُجهَّز
- **أمرٌ واحدٌ في كتلةٍ واحدة** لكلّ خطوة، ليضغطها المالكُ ويرى نتيجتَها قبل التالية.
- **طرفيّتُه PowerShell:** لا `&&` في الإصدار القديم، ولا مساراتٍ بصيغة `/d/…`، ومساراتٌ بشرطةٍ أماميّة `D:/…`. وقبل كلّ شيءٍ قل أين يشغّله (مجلّدٌ مربوطٌ بمشروع Railway). المصدر: `feedback_windows_shell_classifier_pitfalls`، `feedback_user_runs_the_merge`.
- **أنماطٌ بلا قيم:** لا مفاتيحَ ولا عناوينَ ولا معرّفاتِ مشاريع في أيّ رسالةٍ أو ملفّ؛ معرّفٌ شخصيٌّ يلزم الأمرَ يُطلب داخله بـ`getpass` لا يُكتب فيه. المصدر: `feedback_railway_run_vs_ssh`.
- **اشرح مبكّراً** أنّ التنفيذَ بيده — لا بعد محاولاتٍ محجوبة. ثمّ اقرأ مخرَجَه حين يقول «اقرأ الطرفيّة».
- **سؤالٌ طال انتظارُ جوابه** (ساعات): أعِد قراءةَ الحيّ — الوقت، وcommit الإنتاج، ونوافذُ العمليّات — قبل تسليم الأمر، فقد تقادمت فرضيّتُه. المصدر: `reference_deploy_session_recipe_2026_09_26` (الدفعة 9).

## 3) الأنماط
الأسماءُ الثلاثة للخدمات في `.railway/railway.ts` (الويب والعامل وbeat) — هنا `<web>` و`<worker>` و`<beat>`.

| الغرض | النمط | ملاحظات |
|---|---|---|
| النشر | `railway service redeploy --service <web> --environment production --from-source --yes` ثمّ `<worker>` ثمّ `<beat>` | ثلاثُ كتل؛ `--from-source` يبني رأسَ main الحاليّ. متغيّرٌ إلزاميٌّ جديد: الويب وحدَه أوّلاً ثمّ سجلّاتُه ثمّ العاملان |
| قراءةٌ أو أمرٌ على قاعدة الإنتاج | `railway ssh --service <web> --environment production "python manage.py <أمر> [--check]"` | لا `railway run` (يعمل محلّيّاً فلا يحلّ عنوانَ القاعدة الداخليّ ويرسل أخطاءً إلى Sentry). المخرجُ أعدادٌ لا بيانات |
| استعلامُ أثر هجرة | `railway ssh … "python manage.py shell -c \"<عدٌّ أو قيمة>\""` | §02 من هذه المهارة |
| متغيّرُ بيئة | على **الخدمات الثلاث** أو متغيّرٌ مشترك، قبل النشر | لا تقرؤه أنت (يُحجب)؛ تأكيدُ المالك ثمّ سجلّاتُ كلّ خدمة |
| رجوعٌ فوريّ | لوحةُ Railway ← الخدمة ← Deployments ← السابقُ السليم ← Rollback | لكلّ خدمةٍ مسّها التغيير؛ ثمّ `rollback.yml -f verify_only=true` |
| نسخٌ احتياطيٌّ يدويّ قبل عمليّةٍ حسّاسة | `gh workflow run backup.yml` ثمّ `gh run list --workflow backup.yml --limit 1` حتى النجاح | يُسجَّل الوقتُ ورقمُ التشغيل |

المصادر: `feedback_railway_env_all_three_services`، `feedback_railway_run_vs_ssh`، `project_u01_window_runbook_2026_09_28`، `.github/workflows/rollback.yml`.

## 4) ما لا يُقترح أصلاً
- `railway up`: يرفع شجرةَ العمل لا main، ويتجاهل مساراتِ `.gitignore` افتراضاً فأسقط ملفّاً متتبَّعاً (09-26)، وينشر ما لا يطابق main فيعيد النشرُ التالي المعطوبَ. المصدر: `project_railway_cli_upload_incident_2026_09_26`، CLAUDE.md («نافذة النشر»).
- تفعيلُ Auto Deploy أو ضغطُ «Redeploy» من جلسةٍ غير جلسة النشر. المصدر: `feedback_railway_manual_deploy_gate`.
- أمرٌ يجمع حذفاً جماعيّاً (قاعدةٌ ومجلّدٌ وفرعٌ معاً): يُحجب ويحجب ما بعده؛ يُفصل بحسب النوع وبترتيبٍ آمن. المصدر: `feedback_windows_shell_classifier_pitfalls`.
- انتزاعُ تثبيت 8500 من جلسةٍ أخرى (`--force`)، أو `preview.sh up/down` بلا حاجة. المصدر: CLAUDE.md («المعاينة المركزيّة»).

## 5) التغييرات الدائمة (غيرُ الإنتاج)
إعدادُ git عامٌّ أو للمستودع، مهمّةٌ مجدولة، حذفُ أسماءٍ مستعارة: اطلب الموافقةَ بتعداد **كلّ** تغييرٍ حرفيّاً (المفتاح والقيمة والنطاق: عامّ/مستودع/شجرة) وما سيُحذف وأين النسخةُ الاحتياطيّة وأمرُ العكس. «نعم للكلّ» تشمل ما عُدِّد فقط، والمصنِّفُ يحجب ما لم يُعدَّد («Unauthorized Persistence»). المصدر: `feedback_classifier_persistence_needs_enumerated_approval`.

## 6) نصٌّ جاهزٌ للمالك (قالب)
> دفعةُ اليوم اندمجت: main@<sha7> (#A #B #C). المعاينةُ على main سليمة. النشرُ بيدك — ثلاثةُ أوامر، واحداً بعد واحد، من مجلّدٍ مربوطٍ بـRailway:
> (1) الويب … (2) العامل … (3) beat …
> وأنا أراقب النشرات وأشغّل التحقّقَ بعد الثالث وأبلغك بالنتيجة.

## أنماطٌ مضادّة
- تكرارُ محاولةٍ حُجبت بصيغةٍ أخرى.
- «معك صلاحيّة، نفّذ أنت» تُفهم رفعاً للحجب.
- كتابةُ قيمة متغيّرٍ أو عنوانِ الإنتاج في رسالةٍ أو ملفّ.
- كتلةٌ فيها ثلاثةُ أوامر نشرٍ متتابعةٌ فلا يرى المالكُ أيّها فشل.
