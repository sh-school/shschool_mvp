## 2) التوقيت
- **الدمجُ ممنوعٌ آليّاً** الأحد–الخميس 07:00–14:00 الدوحة: وظيفةُ `deploy-window` في `quality-gate.yml` تُسقط مجموعةَ الطابور (`merge_group`) ما لم يحمل الطلبُ وسمَ «نشر-عاجل». فإدخالٌ في النافذة يُقصى ويُعاد بعد 14:00. المصدر: `scripts/deploy_window.py`.
- **الجمعةُ والسبتُ خارج الدوام** — النشرُ فيهما مسموحٌ بلا قيد؛ لا تختلق «لا نشرَ قبل الأحد». وإن رأيتَ سبباً لتأجيلٍ فاعرضه على المالك سؤالاً ولا تعلّق بصمت. المصدر: `feedback_saturday_deploy_allowed`.
- **التجميع:** الأصلُ دفعةٌ تجمع عدّةَ طلباتٍ فتقلّ إعاداتُ التشغيل (CLAUDE.md، «نافذة النشر»)، وأجاز المالكُ 09-25 دفعاتٍ متعدّدةً بعد الدوام حين يلزم. المصدر: `feedback_deploy_batches_and_urgent`.
- **نوافذُ عمليّات المالك على الإنتاج** (مثل تشغيل أمر إصلاحٍ على البيانات): لا نشرَ ولا إعادةَ تشغيلٍ ولا تغييرَ متغيّراتٍ في ساعتها، وتحقّق قبلها أنّ لا نشرَ جارياً. المصدر: `project_u01_window_runbook_2026_09_28`.
- احجز استباقيّاً: طلبٌ جاهزٌ قبيل 07:00 يبقى خارج الطابور حتى 14:00 — ويجوز للمالك أن يأمر بتجاوز ذلك بنصّه. المصدر: `reference_deploy_session_recipe_2026_09_26` (الدفعة 7).

## 3) الاستعجال داخل الدوام
1. إذنُ المالك الصريح لهذا الطلب بعينه (لا إذنٌ عامّ ولا منقول).
2. `gh pr edit <N> --add-label نشر-عاجل` ثمّ الإدخالُ كالمعتاد.
3. التحقّقُ كاملاً كأيّ دفعة؛ والوسمُ لا يُعفي من سطر الاعتماد ولا من قراءة الفرق.
المصدر: `project_deploy_window`، `feedback_deploy_batches_and_urgent`.

## 4) الإذنُ الدائم بالنشر
قال المالكُ 09-28: «انشرها كلها اذا تم الدمج» — فلا تسأله «هل أنشر؟» بعد كلّ دمجٍ اكتمل تحقّقُه، بل جهّز الأوامرَ ونبّهه. لا يُلغي هذا سطرَ الاعتماد ولا النافذة ولا الحجوز. المصدر: `reference_deploy_session_recipe_2026_09_26`.

## 5) الدورة بالأوامر (قراءاتٌ إلّا ما وُسم)
```bash
# الحال
bash scripts/preview.sh status                      # main مقابل commit الإنتاج وما ينتظر
gh api graphql -F owner='{owner}' -F name='{repo}' -f query='query($owner:String!,$name:String!){repository(owner:$owner,name:$name){mergeQueue(branch:"main"){entries(first:20){nodes{state pullRequest{number}}}}}}'
# البوّابة لكلّ طلب ثمّ الفرقُ الفعليّ
python .claude/skills/schoolos-deploy/scripts/pr_gate.py <N> [<N> ...]
git fetch origin && git diff origin/main...<headRefOid> --stat && git diff origin/main...<headRefOid>
# محاكاةُ السلسلة بأبٍ واحد (squash) قبل إدخال طلباتٍ متعدّدة
python ~/deploy_work/simulate_chain.py <N1> <N2> ...
# الإدخال (فعل): أمرٌ صريحٌ لكلّ طلب
gh pr merge <N> --auto
# المراقبة: الطابور وmerge_group وmain
bash ~/deploy_work/queue_watch.sh      # في الخلفيّة، سطرٌ كلَّ دقيقة
gh run list --event merge_group --limit 20
```
- `gh pr merge` بلا `--delete-branch` (الطابورُ يرفضه ويحذف الفرعَ بنفسه). المصدر: `project_merge_queue`.
- الطابورُ يعيد الفحوصَ على «main + الطلب» ≈15 دقيقة لكلّ مجموعة. المصدر: `reference_deploy_session_recipe_2026_09_26`.
- لا سكربتَ يتحقّق ثمّ يدمج في حلقة: المصنِّفُ حجبه («Blind Apply») حتى أذن المالكُ بنصّه، والأسلمُ أوامرُ صريحةٌ بعد قراءةٍ حيّة. المصدر: مثله (تحديث 09-26).
- بعد اكتمال الدفعة على main: `bash scripts/preview.sh sync --now` ثمّ دخانٌ على المعاينة (سكربتا `preview_export_smoke.py` و`preview_login_path_smoke.py` في `deploy_work` عبر `manage.py shell` داخل حاوية المعاينة) و`manage.py check`. المعاينةُ لا تعكس التخزينَ والبريدَ وbeat وبياناتِ الإنتاج (`docs/deployment/local_preview.md` §5).
- ثمّ النشر (`04-owner-only-commands.md`) والتحقّق (`02-post-deploy-verification.md`).

## 6) ترتيبُ الدفعة
- **المتراكب** (فرعٌ مبنيٌّ على فرع طلبٍ آخر) يتعارض في الطابور لأنّه squash: أساسُه أوّلاً، ثمّ يدمج صاحبُه origin/main في فرعه بلا force ويتحقّق بـ`git diff origin/main...HEAD`، ثمّ يدخل. `simulate_chain.py` صار بأبٍ واحدٍ لهذا السبب. المصدر: `reference_deploy_session_recipe_2026_09_26`.
- **حاملُ حارسٍ جديد** يُدمج **بعد** ترحيل الملفّات التي سيرفضها، لا قبله. المصدر: مثله (#705 و#704).
- **متداخلان في ملفّ** (أشهرُها `docs/governance/regression_guards.md`): الثاني لا يدخل حتى يندمج الأوّل ويحدّثه صاحبُه. وظيفةُ `pr-file-collision` تحذّر ولا تحجب. المصدر: `feedback_publish_session_merges_all`، `scripts/pr_file_collision.py`.
- **هجراتُ التطبيق الواحد المتوازية** (رقمان متتاليان من فرعين): تنبّه لتسلسلها وتصادم ترقيمها قبل الدمج. المصدر: `feedback_publish_session_merges_all`.
- **تحديثاتُ التبعيّات الآليّة** (dependabot) لا تُدمج ما لم يُطلب نشرُها. المصدر: `reference_deploy_session_recipe_2026_09_26`.

## 7) ما بعد الدفعة
تسليمٌ مكتفٍ بنفسه لـ«0701 · تحديث الخارطة» و«0702 · مراقبات الجودة» ولأصحاب الطلبات: main الجديد، والطلباتُ وأصحابُها، وما تحقّق وكيف، وما بقي. تفصيلُه في `02-post-deploy-verification.md` §5.

## أنماطٌ مضادّة
- إدخالُ طلبٍ في يوم دوامٍ قبل النظر في الساعة، ثمّ تفسيرُ الإقصاء عطلاً.
- دفعةٌ تُطلق بينما طلبٌ مشروطُ النشر في main — كلُّ ما بعده يتعلّق معه.
- إدخالُ طلبٍ جديدٍ أثناء نشرٍ جارٍ ظنّاً أنّه «سيلحق» — `--from-source` يبني رأسَ main وقتَ الإطلاق، فإمّا يُفوّت وإمّا يُنشر بلا تحقّق.
- تأجيلُ نشرٍ جاهزٍ بلا سؤال المالك.
