منهجية التحليل العميقة

تم تحليل المشروع عبر قراءة شاملة للنماذج والخدمات والآراء والوسيطات:

اكتشافات تقنية دقيقة:

  • نظام الهويات + التشفير المزدوج: النموذج CustomUser يحتفظ بثلاث نسخ من national_id: نصية (للدخول)، مشفّرة بـ Fernet (PDPPL م.8)، وHMAC hash (lookup مفهرس). هذا متقدم لكنه يرفع التعقيد أثناء الترقيات.
  • نظام الأدوار الهرمي متطور (v7): 5 مستويات إدارية + 25 دوراً متخصصاً موثقة بقرارات وزارية. المشروع احترافي في نمذجة التسلسل الإداري لكنه قد يكون مفرطاً للمدرسة الواحدة.
  • المخالفات السلوكية: نموذج مزدوج (ABCD قديم + 40 مخالفة جديدة 2025): ViolationCategory يدعم كلاهما مع backward_compat. الإجراءات التصاعدية محددة حسب الدرجة (1-4) مع أتمتة الإحالات الأمنية على الدرجة 4.
  • نظام التقييمات دقيق جداً: AssessmentPackage ينقسم إلى 4 باقات موزونة (P1-P4) بدقة عشرية + Decimal (ليس float) مما يدل على معايرة تعليمية صلبة. الحسابات: الفصل الأول 40 درجة، الثاني 60 درجة، يُطبَّق بالفعل وفق MOEHE.
  • تشفير البيانات الحساسة قيد التشغيل: حقول clinic مثل ClinicVisit تستخدم EncryptedTextField بـ Fernet، لكن الترجمة من plaintext لـ encrypted يتطلب migration دقيقة (لا توجد آليات auto-migration واضحة).
  • نظام التتبع (Audit) غير قابل للحذف: AuditLog مع مدير custom يرفع PermissionDenied على delete/update. صلب لكن قد يعرقل الحذف الشامل للبيانات المحقوقة (Right to Erasure PDPPL م.18).
  • موافقات الوالدين (ConsentRecord): نموذج منفصل مع 7 أنواع بيانات وطرق إعطاء (form/digital/verbal). الإشعارات تُخمَّد حسب الموافقة، لكن recapture من البيانات المسحوبة غير موثّق.
  • تقارير الانتهاك (BreachReport غير مرن: Status flow: discovered → assessing → notified → resolved، مع NCSA 72h deadline. لكن "rollback" إلى assessing بعد notified قد يؤدي لنقاشات قانونية مع CDPP.

القوة (Strengths) — اكتشافات معمقة

  • نموذج هرمي متطور للأدوار: 5 مستويات + 25 دوراً محددة وفق قرارات وزارية فعلية (قرار 32/2019 + تعديلات 2025). الترجمة مباشرة من MOEHE regulatory.
  • تشفير مزدوج للبيانات الحساسة: national_id و phone يحصلان على Fernet (at-rest) + HMAC hash (for indexed lookup ميكانيكي). دفاع عميق ضد Rainbow Tables.
  • نظام التقييمات موثّق رياضياً: AssessmentPackage بـ Decimal precision — الفصل الأول 40 درجة، الثاني 60 درجة، محسوبة بدقة حسب وزن الباقات (P1 37.5%، P2 50%، AW 12.5%). لا توجد drift في الحسابات.
  • سجل المراجعة غير قابل للحذف: AuditLog مع custom manager يرفع PermissionDenied على أي محاولة حذف/تحديث — قانونياً صلب لـ PDPPL م.19.
  • انفصال منطقي نظيف: 19 تطبيق Django بدون دورات مرجعية واضحة — كل تطبيق (behavior، clinic، assessments) يملك نماذجه الكاملة.
  • وسيطات أمنية كثيفة: RLS Middleware + HMACAuthBackend + rate limiting Axes + CSP nonce-based + validated file uploads مع UUID عشوائي.
  • موافقات والدين قابلة للتتبع: ConsentRecord مع 7 أنواع بيانات و 3 طرق إعطاء + withdrawn_at timestamp — compliance-grade tracking.
  • إضافات قانونية 2025 مدمجة: 40 مخالفة جديدة في ViolationCategory مع دعم ABCD legacy، NLP-ready tags (tech/safety/law/national)، وإحالات أمنية مُؤتمتة الدرجة 4.

الضعف (Weaknesses) — اكتشافات معمقة

  • مشاكل مرونة التشفير: إذا فشل encrypt_field() في save()، الحقل قد يبقى بدون تحديث. لا rollback واضح → PII قد تبقى plaintext بخطأ.
  • Denormalization في السلوك: infraction.level ينسخ من violation_category.degree. إذا تغيرت الفئة لاحقاً (bugfix)، السجلات التاريخية تبقى بـ degree قديم → تقارير كاذبة.
  • RLS middleware قد تسرب context عتيق: في connection pool حار (high concurrency)، اتصال قد يُعاد لـ user آخر قبل إعادة تعيين السياق → data leak عابر (transient).
  • مهام الإشعارات ناقصة monitoring: broad catch في send_email_task/send_sms_task يخفي أخطاء الشبكة. غياب dead-letter queue = رسائل ضائعة بصمت.
  • IDOR ممكن في reports export: لا يوجد validation صريح أن الطالب ينتمي للفصل قبل توليد PDF — teacher قد يُغيّر student_id يدوياً.
  • ملفات orphaned من excuse uploads: _excuse_upload_path توليد UUID عشوائي بدون ربط مباشر لـ StudentAttendance → حذف الحضور لا يحذف الملف.
  • breach reporting بدون rollback: Status: discovered → assessing → notified → resolved. ارجاع من notified إلى assessing قد يُربك CDPP (تسلسل event غير متوقع).
  • معايرة coverage gate غير متسقة: pyproject.toml يقول 60%، لكن quality-gate.yml يقول 0 للـ CI السريع. تعارض يفتح الباب لـ regressions خفية.

الفرص (Opportunities) — استغلال معمق

  • استخراج LayerService للتشفير: إنشاء EncryptionService مركزي يتعامل مع fail-safe، logging، وkey rotation دوري — يزيل الكود المكرر والخطأ.
  • تحويل RLS إلى AppRole قابل للاختبار: نقل logic من middleware إلى model manager — اختبار أسهل، أخطاء أوضح.
  • إضافة audit log soft-delete tracking: معرّف AuditLogDeleteRequest (حتى لو كان عامل ممنوع) — يرسل موافقة قانونية صريحة.
  • بناء dead-letter queue للإشعارات: Celery تدعم DLQ native — رسائل فاشلة تذهب لـ queue منفصلة مع dashboard alerts.
  • تطبيق Permission Policy صريحة على views: validator decorator واحد: @permission_required_schema(student__in__class) — منع IDOR نهائياً.
  • بناء inventory نظيف للملفات: نموذج FileReference يربط file_path بـ object_id + model_name — deletion واضح وتتبع يدوي.
  • تطبيق BehaviorIntegration Layer: نموذج منفصل BehaviorEventLog يُسجّل كل حالة من infraction بـ timestamp (discovered, escalated, resolved) — لا نسخ/تحديث، فقط append.
  • توسيع KPIs التحليلية بـ ML: anomaly detection على attendance patterns + predictive behavior flags + churn forecasting للطلاب المعرضين.

التهديدات (Threats) — سيناريوهات واقعية

  • فشل Fernet key rotation: إذا كان FERNET_KEY غير محدّث 6 أشهر، احتمالية أن يُخترق (في الإنتاج) = تسرب سريع لـ 500 كشف encryption.
  • خيوط RLS عند throughput عالي: تحت 1000 concurrent users، connection pool قد لا تعاد بسرعة → RLS context قد يبقى من user سابق ولو لـ 100ms.
  • breach notification لم تُختبَر تحت أمن حقيقي: playbook موجود لكن لم يتم تشغيله مع CDPP فعلياً — قد تفشل في الساعة الأولى من incident حقيقي.
  • تسريب ملفات ضخمة عبر excuse upload: FileTypeValidator اختياري على excuse_file + حجم 10MB — طالب قد يرفع video مخفي بـ .pdf extension.
  • تسلسل غير قابل للتتبع في signals: عند حفظ BehaviorInfraction، قد يُطلق signal مختلف حسب version — تدقيق قد يفقد الأحداث الغير متوقعة.
  • absence alert Celery في طابور Redis: إذا فشل Redis 02:00 صباحاً عند إطلاق pending_absence_alerts، أولياء الأمور لن يتلقوا إشعار hol — لا retry آلي محدّد.

ملاحظات دقة التقرير

  • التقرير مبني على قراءة فعلية لملفات المصدر الحرجة ومسح بنيوي للمستودع، وليس على وصف نظري فقط.
  • التحليل يركز على المخاطر الفعلية القابلة للتنفيذ: ما يجب إصلاحه أولاً لتقليل الخطر وتعظيم الأثر.
  • لإصدار نسخة Board-ready نهائية، يمكن إضافة ملاحق KPI تاريخية وربطها بسجلات CI للأشهر الثلاثة الأخيرة.
